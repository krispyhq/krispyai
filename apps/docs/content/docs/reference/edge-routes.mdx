# edge routes

one Cloudflare Worker hosts all of these plus the `SessionDO`. CORS allow-origin is
`ALLOWED_ORIGIN` (default `*`); `OPTIONS` is answered for every route.

## public routes

| method | path                             | body / query → response                                                                                                                           |
| ------ | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST` | `/api/chat`                      | `{ sessionId, message, tenantId?, history? }` → `{ reply, handoff, handoffState, handedOff, degraded?, formId?, form? }`                          |
| `POST` | `/api/contact`                   | `{ sessionId, tenantId?, name?, contact?, message? }` → `{ ok: true }` — legacy contact-capture shim (maps onto the lead fan-out)                 |
| `POST` | `/api/lead`                      | `{ tenantId?, sessionId, formId?, values, history }` → `{ ok: true }` — a form's captured values fan out to delivery connectors                   |
| `GET`  | `/api/session/:id/ws?t=<tenant>` | WebSocket upgrade → `SessionDO`. `426` if not an upgrade. the visitor's live channel                                                              |
| `GET`  | `/api/widget/config?t=<tenant>`  | → `{ capabilities: { attachments }, theme, ctas, script, popups }` — the **public, secret-free** widget projection (whitelist only; no `persona`) |
| `GET`  | `/api/usage?t=<tenant>`          | → `{ tenantId, usage: { ai, handoff, tokens }, plan, entitled, status, limits, withinLimits }`                                                    |
| `GET`  | `/health`                        | → `{ status: "ok", service: "edge" }`                                                                                                             |

### `POST /api/chat` gate

before answering, the Worker checks entitlement + plan limits. self-host (`"self"`) is
always entitled and unmetered. a non-self tenant with no valid snapshot gets
`402 { error: "subscription_required" }`; over its cap it gets
`429 { error: "usage_limit_reached" }`. missing `sessionId`/`message` → `400`.

`handoffState` is explicit: `ai` answers; `pending` means a human was notified but has not
replied; `operator` starts with the first human reply. Pending and operator-owned visitor
messages still reach the topic and server ring, while the AI stays silent. `handedOff` remains
as a compatibility boolean and is true only for `operator`.

Telegram is optional for the Buttr inbox. Before moving a session to `pending`, the Worker writes
`handoff:<tenant>:<session>` to KV. Topic links keep their separate legacy `session:` keys, so
enabling Telegram later cannot overwrite discovery state. The inbox unions and de-duplicates both
prefixes so conversations created before this index remain visible.

Known business questions stay with the AI. An explicit human request enters `pending` immediately
without requiring a name, email, phone, or order reference. Only a business-configured form can
collect details. Screenshot paste/drop is advertised only when `capabilities.attachments` is true;
the current attachment transport remains Telegram-backed.

`history` is client-supplied context and may include the current visitor message as its final
`user` entry (the browser widget sends it that way). When an empty session is handed off, the
Worker seeds only prior history and appends the live visitor turn once. It removes one trailing
exact match only; earlier repeated messages remain separate turns.

## secret-guarded routes

these carry a bot token or mutate config, so they require a shared-secret header. a missing
or wrong secret returns **401** (config routes) / **403** (webhook, billing) and leaks nothing.

| method | path                                             | auth header                                                  | purpose                                                                                                                                                                                                                                                                                       |
| ------ | ------------------------------------------------ | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST` | `/api/telegram/webhook`                          | `x-telegram-bot-api-secret-token: <TELEGRAM_WEBHOOK_SECRET>` | owner's Telegram reply → push to the visitor via the DO, move `pending` → `operator`                                                                                                                                                                                                          |
| `GET`  | `/api/tenant/config?t=<tenant>`                  | `x-tenant-sync-secret: <TENANT_SYNC_SECRET>`                 | read a tenant's full config `{ botToken, chatId, systemPrompt?, model?, ... }` (404 if none)                                                                                                                                                                                                  |
| `POST` | `/api/tenant/config`                             | `x-tenant-sync-secret: <TENANT_SYNC_SECRET>`                 | `{ tenantId, config }` → **merge** into the tenant's KV config. the CLI writes here. out-of-bounds configs are hard-rejected: oversized avatar/kbSources → `413`, bad avatar scheme or non-https CTA url → `400` (see [tenant config → write caps](/docs/reference/tenant-config#write-caps)) |
| `POST` | `/api/billing/entitlement`                       | `x-billing-sync-secret: <BILLING_SYNC_SECRET>`               | mirror an entitlement snapshot into KV (for a hosted/multi-tenant deploy; unused in self-host)                                                                                                                                                                                                |
| `GET`  | `/api/tenant/liveness?t=<tenant>`                | `x-tenant-sync-secret: <TENANT_SYNC_SECRET>`                 | "is my widget live?" — returns `{ seen: { at, origin?, url? } \| null }`, the last time the widget booted on a customer page (stamped, throttled per site and embedding origin, off every `GET /api/widget/config`) + the embedding origin/url. `null` until it phones home                   |
| `GET`  | `/api/tenant/kb-suggestions?t=<tenant>&s=<site>` | `x-tenant-sync-secret: <TENANT_SYNC_SECRET>`                 | list pending relearning suggestions → `{ suggestions: KbSuggestion[] }` (machine-proposed Q→A from operator-touched sessions; own KV key `suggestions:<ns(t,s)>`, never public)                                                                                                               |
| `POST` | `/api/tenant/kb-approve`                         | `x-tenant-sync-secret: <TENANT_SYNC_SECRET>`                 | `{ tenantId, siteId?, id }` → move the suggestion into `kbSources` (+ bump `kbVersion`) and drop it from pending → `{ ok: true, source }`. `404` if the id isn't pending                                                                                                                      |
| `POST` | `/api/tenant/kb-dismiss`                         | `x-tenant-sync-secret: <TENANT_SYNC_SECRET>`                 | `{ tenantId, siteId?, id }` → drop the suggestion, no KB change → `{ ok: true }`                                                                                                                                                                                                              |

<Callout type="warn">
  `GET /api/tenant/config` returns the **full** config (bot token included) and is secret-guarded.
  `GET /api/widget/config` is the public read the browser uses — it returns **only** the whitelist
  (`capabilities`, `theme`, `ctas`, `script`, `popups`) and never the token/prompt/persona. don't
  confuse them. see [security](/docs/security).
</Callout>

<Callout>
  **Multi-site.** An account can run multiple sites, each with its own config/kbase/branding.
  Pass an optional `?s=<siteId>` (query, on `config`/`liveness`) or `siteId` (body, on
  `chat`/`lead`/`tenant/config`) to scope to a site. Absent → the account's default site
  (the bare `tenant:<t>` key), so existing embeds are unchanged. `siteId` is
  `[a-z0-9_-]{1,40}`; anything else → `400`. Conversations and billing stay account-scoped.
</Callout>

## the SessionDO (internal)

the Worker forwards to a `SessionDO` per `(tenant, session)`; the browser never calls it
directly. its surface: the WebSocket upgrade (visitor connects, receives
`{ type: "ready", handoffState, handedOff }`), `GET /state` (`{ handoffState, handedOff }`),
`POST /context { tenantId, siteId? }` (the chat flow's combined
`{ handoffState, handedOff, messages }` read — the body persists the tenant's
identity into DO storage **write-once** so the relearning handback, which fires from an alarm
with no request in flight, can build the per-site `suggestions:` key + meter the AI call),
`POST /operator {text}` (move pending → operator and broadcast the reply), and `POST /handoff`
(move ai → pending and broadcast the waiting state). `POST /resolve` and silence handback move
either human state back to ai. server → browser events: `ready`, `operator`, `handoff`, `resume`.
On reconnect, `pending` renders a truthful waiting message; only `operator` says a team member
joined.

**Relearning.** On a real handback (operator had the session, then it resolves or the silence
alarm fires) the DO makes **one** Workers-AI call to extract a Q→A the human answered that the
bot couldn't, and appends it (normalized-question dedup, FIFO cap 20) under
`suggestions:<ns(t,s)>` for a human to approve via `/api/tenant/kb-approve`. **Off by default:**
it runs only for tenants using the knowledge base (≥1 `kbSource`) — a tenant that never
configured a KB incurs zero AI cost on handback. Also gated on ≥1 operator message; failures are
swallowed (never break resolve). The bot never self-modifies its KB — approval is a human click
(a prompt-injection valve).

## keeping this in sync

the repo mirrors routes into a Bruno collection (`api-collection/`). when you add or change
a route, update the matching `.bru` request in the same change (per `CONTRIBUTING.md`).

### Launcher appearance in public config

`GET /api/widget/config` includes `theme.launcherStyle` (`circle` or `pill`) and
`theme.launcherLabel` when configured. The widget displays up to 24 label characters;
unset fields retain the circular launcher. These fields contain public display text,
not credentials. Configure them through the authenticated tenant-config endpoint.

### Hosted owner notifications

The hosted edge needs `PUSH_TOKENS_URL` set to its matching cloud API
`/internal/push/tokens` endpoint and `PUSH_TOKENS_SECRET` set to the shared
server credential. The preview deployment config supplies the preview endpoint.
Without the URL, chat and inbox persistence work but mobile push is skipped.
A signed device build, notification permission, registered device token, and
valid platform push credentials are also required; simulator chat tests do not
prove notification delivery. Self-hosted installations may leave these unset.
